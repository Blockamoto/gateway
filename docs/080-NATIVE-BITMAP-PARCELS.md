# Standard Parcel JSON composition

The enabled native replay Parcel track now executes a complete ordered JSON
program through the shared compiler and typed interpreter. Three actual
documents, `bitmap-parcels-standard-v1-{retained-raw,tx-locators,txio-links}.json`,
pin the chosen proof provider. They declare the exact Standard District winners
checkpoint, block-context and inscription-identity points, and checked parent
replay points. The inspector exposes these documents for saving and editing.

Ordinary byte/MIME/decimal/list/state operations control claim grammar,
recognized District matching, same-block recognition order, target transaction
bounds, declared-parent membership, checked relationship acceptance, rejection
reasons and first eligible winner selection. Candidate records and source
availability hints are explicit JSON values. The program reads a proof only
after the cheaper predicates establish that it is relevant. The earlier
candidate-only document remains available as a separate partial tracker.

The native adapter supplies read-only source inputs, maps typed proposals to the
existing candidate/winner/target codecs, and retains the existing publication,
profile, route admission and recovery contracts. It performs no claim grammar
or winner selection. JSON availability hints supply the existing pending
presentation. Replay Parcels still publish no provisional journal or coverage
when a required source is unavailable. The deferred and historical profiles keep
their original gates and code paths.

Saved copies execute through general ordered table generations. Used District
facts, point results and relationship proof blobs belong to the child, with
their existing checkpoint, query, archive, recovery and collection contracts.
A saved copy can instead pin an explicitly chosen saved District table. Its
definition does not start that parent or any historical proof producer.

The public full-copy check uncovered a final admission check that still resolved
only built-in Coin definitions. It now uses the common built-in resolver, so an
exact Standard District pin survives review/start. Existing Coin checkpoint
forms use the same resolver.

Parent identity lookups keep a bounded current-inventory index and one historical
inventory index. Different current-child point reads reuse the admitted current
inventory rather than reparsing the whole block for each candidate. Cancellation
does not publish a partially constructed inventory index.

Validation separates its evidence:

- Controlled already-checked facts exercise verified and rejected relationships,
  two first winners, a duplicate, transaction bounds, absent/not-yet-recognized
  Districts, unmatched declarations and malformed/future claims. These are policy
  unit inputs, not authenticated Bitcoin evidence.
- Native comparisons against the frozen implementation match complete heads,
  COW references and pending behavior on malformed and real source fixtures.
  Provider-only variants produce the same physical four-candidate fixture.
- The public saved full program runs on authenticated block 792435 with one
  cohort source read, a retained District dependency and independent custom
  suffix behavior. That real block contains **zero Parcel candidates** in this
  check; it is an authenticated covered-empty case, not a positive Parcel proof.
- The separate three-block mainnet Ord relationship fixture exercises genuine
  checked replay, source replacement and owned proof lifecycle. It is not a
  Bitmap claim or a complete genesis-prefix producer.
