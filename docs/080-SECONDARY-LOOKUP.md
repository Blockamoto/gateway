# Generic recipe secondary-key lookup proposal

Status: private bounded prototype in `recipe_secondary.go` and `recipe_secondary_local.go`. Explicit callers may stage an immutable secondary receipt; there is no scheduler, public API, UI or native TX ID Locators integration. Production exposure and full-chain efficiency remain unverified.

## Purpose and scope

A generic opt-in descriptor identifies one existing generic recipe table and one text-valued key selector: initially either its declared primary key or a named text column. The exact compiled program must match the source generation, and every write to the selected table must supply that selector as guaranteed text; unknown, missing, optional, invalid or non-text selectors are rejected. The descriptor, source semantic fingerprint, encoding version, and value type define the index identity. It is not a built-in index name or a whole-index operation. An explicit build covers a bounded height interval and only the committed sparse units within that interval. Empty evaluated units contribute coverage without postings. A missing match means no match **within the authenticated indexed coverage**, not absence from unprocessed blocks.

For `recipes/tx-id-locator.json`, select table `transactions`, primary key `txid`. A posting carries the original composite row key, height, block hash, and immutable unit digest. The returned row supplies its `ref` (`txIndex.height`); every occurrence is retained. Thus identical txids in two heights produce two distinct postings, and multiple rows at one height may share a secondary column. No uniqueness assumption or last-writer-wins replacement is permitted.

## Immutable snapshot and keys

Reuse `ordinalTree` (hex-only keys, 128-character maximum, immutable content-addressed pages), not a new path based on user-controlled keys. The outer key is the full SHA-256 digest of a domain-separated canonical `(descriptor, typed lookup value)`. Its value names an immutable postings-tree root plus enough original typed value and descriptor identity to verify the digest. A postings key is fixed-width hexadecimal height (16 characters) followed by the full SHA-256 digest of the exact composite row key (64 characters). Store the original row key and exact value in the posting; validate them on insert/read and fail closed on any same-digest/different-value collision. This permits bounded prefix/range traversal and stable ordering by height then row-key digest, without truncating hashes or exceeding the radix key limit. Canonical scalar encoding and size bounds must be specified before accepting types beyond text; different JSON types, missing, null and invalid must not silently coalesce.

A snapshot receipt binds the immutable postings root and descriptor to the source instance, semantic fingerprint, exact `recipeStoreHead` checksum, root and revision, indexed interval, and a selected-local-header prefix token `(height, hash)`. The token authenticates ancestry through that height, not full Bitcoin consensus. The receipt also records coverage: a sparse authenticated set of block anchors, or a separately validated proof of that set. It cannot infer contiguous coverage from the greatest processed height. No dependent recipe row is indexed unless its full lineage is separately validated under the same snapshot; initially reject lineage-bearing units.

## Build and publication

A build is an explicit operation on an already committed source generation, currently bounded to 4,096 units, 8,192 postings, 32 MiB of staging metadata and 64 MiB of source-unit data. Capture the store head and selected header prefix; enumerate the source height tree with bounded, cancellable pages. For each referenced unit, validate its checksum, exact height/hash and every selected-chain anchor; derive postings in bounded batches. Stage immutable pages and receipts outside reader-visible heads. At final publication reacquire the established header → registry → store lock order, reject a reconciliation fence, recheck the exact source head, saved revision/semantic receipt and selected prefix, write the content-addressed receipt, then publish a separate immutable application marker last under the guard. A receipt without that marker is incomplete staging. The marker follows the primary store’s application-controlled-profile trust model; it is not a signature against an actor who can forge profile files. Re-read/check it before use. Interruption may leave unreachable immutable files only; it must never replace or repair existing data silently.

There need not be a second mutable authoritative head: address a ready secondary receipt by its exact source head and descriptor identities. If no matching complete receipt exists, return `unavailable` or `stale`, never a partial answer presented as complete. On any source publication, backfill, reconcile, reorg, changed lineage or descriptor/profile change, the old receipt is automatically ineligible because its source or chain token differs. A subsequent explicit rebuild may reuse verified immutable subtrees, but reuse is an optimization with proof, not a prerequisite for correctness. A later integrated single-head schema can update primary and secondary roots atomically per block; it must preserve old schema heads and provide an explicit migration.

## Query, paging and authority

Hold the normal selected-header and registry fence while validating the saved recipe revision, exact primary head and receipt identities. Recheck the selected prefix token and reject any active reconciliation fence. Recheck the availability and checksums of all bounded covered primary units, including for negative results. Read a bounded page of the matching postings tree, then verify each posting against its source height reference and immutable unit, exact table/key/value and selected block hash. Return the original row or an authenticated pointer, not an unverified hash-to-location claim. Include indexed scope and coverage limitations in every response. Return distinct states for unavailable index, stale snapshot, uncovered range, and a complete empty result for covered units.

A continuation token binds the secondary receipt and typed query value and the last postings key, which must exist in the bucket. It represents a caller-controlled start-after position rather than proof that an earlier page was displayed; the content-addressed receipt binds the descriptor, exact primary head revision/root, selected prefix and saved definition revision. Enforce strict key, offset, read-page, result-byte and CPU/cancellation limits. A changed source head, chain prefix, recipe revision or unit makes every old token stale. Release locks before sending HTTP bytes. No query starts a build, fetches blocks, arms a track or modifies history.

## Required validation before enabling

- Compare every posting and absence/coverage state with independently executed 0.7.9 locator results over the same verified blocks; include transaction duplicates across heights, multiple equal column values in one block, and a real 908657 fixture. Distinguish native lookup semantics from generic block-scoped evidence.
- Test sparse holes, empty units, disjoint ranges, explicit backfill, restart, finite and Live extension; all coverage and result paging must remain pinned to one revision.
- Test reorg before/during build, after receipt publication and between pages; selected-header, unit, saved-revision and admission changes must fail closed. Include dependency lineage only after its full fence is designed.
- Inject crashes before/after page, receipt and source-head writes; old heads and units remain readable, interrupted staging never appears complete, and deletion or corruption of any reachable page/receipt is an error rather than an empty result.
- Test adversarial key encodings, exact scalar typing, duplicate keys/digest collisions, bounded work for large result sets and long-common-prefix radix pages, cancellation, slow HTTP consumers, and lock ordering. Benchmark incremental maintenance before presenting this as suitable for a full-chain locator.
