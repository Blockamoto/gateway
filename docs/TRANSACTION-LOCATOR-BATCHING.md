# TX ID Locators physical batching

The full TX ID Locators coordinator can stage its normal per-block records in genesis-aligned logical windows of 336 blocks. Every Bitcoin transaction is retained, including transaction zero and coinbase transactions. The source block, transaction order, existing profile/rule identity, checkpoint calculation, immutable commit JSON, and previous-commit chain remain unchanged.

Physical staging has separate limits: 32 MiB of serialized commit JSON or 400,000 encoded locator records. Crossing a limit flushes the existing stage before admitting the next block. A single verified block may exceed a soft limit, but its serialized commit must fit the existing 64 MiB hard limit. Record payloads use flat buffers grouped by four hexadecimal digits. These are payload limits, not an RSS limit; Go maps and buffer capacity add overhead. Staging does not retain decoded blocks. Publication guards use independent, cancellable contexts containing only admission and source-anchor metadata.

`checkpoint` and `head` on the writer may describe staged logical progress. `DurableCheckpoint` is the published prefix. A flush writes the unchanged immutable commits, then locator data and receipts, then the active membership table, and finally the atomic head. The coordinator flushes partial windows at reviewed boundaries and discards unpublished staging when cancelled or reconciliation is needed. A failed flush can be retried; acknowledged locator rows are deduplicated on replay. A successful head replacement followed by an enclosing-directory flush error is reported and can finish that acknowledgement without appending its records again.

New batched acceleration uses 256 outer-prefix append buckets under `locators-packed-v1`. Frames for each inner prefix form a decreasing, hash-linked chain. Each frame has its own digest and CRC, and the bucket receipt acknowledges its byte prefix and inner heads. A transaction lookup follows only its inner chain, authenticates the requested frames, and merges any legacy shard rows. Total lookup bytes are bounded at 64 MiB, with the existing bounded match count. Missing or damaged evidence produces an error or unknown result; it does not establish absence.

The head's additive `locator_layout: packed-buckets-v1` selects `active-packed-commits.bin`. Batched publication does not advance the legacy `active-commits.bin` ready marker. An older binary that ignores the new field therefore finds its own marker missing or behind the head and must reconstruct legacy acceleration from the unchanged immutable commits before answering. If that binary then extends or reconciles the index, the next upgrade refreshes packed membership from its authoritative legacy prefix, even when an older packed table is present. This preserves rollback readability through reconstruction; it does not make packed acceleration directly readable by older versions.

Physical-operation counters distinguish commit writes, acknowledged bucket/shard append groups and file syncs, successful receipt replacements, active-table writes, head writes (including reconciliation), records/bytes appended, and flush time from logical block and transaction progress. A receipt replacement is counted even when its later directory acknowledgement fails. A replay that finds every row already present still retries the file/directory acknowledgement before publishing the head. Windows replacement uses the existing write-through locator primitive; the implementation does not claim unsupported hardware power-loss guarantees.
