# Bitcoin first contact: independent source audit

Research date: 2026-09-26. This is a source review and proposed experiment design, **not an executed stock-Core topology experiment**. No claim here measures deployment prevalence, real-world discovery latency, or the incidence of misleading service masks.

## Decision

**Bit 25 can be a useful candidate hint, but it is not a sufficient standalone bootstrap mechanism for a Gateway-only listener.** Stock Core v31.1 drops incoming gossip addresses carrying only bit 25 before storing or relaying them. Bitcoin-first discovery remains conditionally plausible where reachable Gateway-capable Bitcoin endpoints truthfully provide Bitcoin services acceptable to Core, and those addresses actually enter the sampled address population. More aggressive crawling cannot recover an address absent from that population.

The architectural consequence is not to fake Bitcoin flags. Specify the entrance deployment model and prove propagation before tuning a heat-seeking scheduler. A Gateway-only node can consume Bitcoin address discovery; that does not imply other Bitcoin nodes will propagate its own address.

### Mask cases and what they mean

| Advertisement | Interpretation for this audit |
|---|---|
| `1 << 25` alone | Does not cross the stock-Core incoming address filter; an already known direct endpoint may still be probed. |
| Bit 25 plus truthful NETWORK/LIMITED | Can cross the service portion of the receive filter; routability, freshness, rate limits, reachable networks, bucket admission and later expiry still matter. Full outbound selection has further requirements. |
| All 64 bits set | Includes the required Bitcoin flags and bit 25; therefore a bit test cannot distinguish it from a precise claim. Mark as suspicious evidence and cap its priority. |
| Precise bit-25 lie | Also possible; excluding the all-bits mask does not solve false advertisements. |
| Same claim repeated by many introducers | Could be a copied rumor, not independent corroboration or independent identities. |

Because gossip service masks are unioned, a false bit can attach to an otherwise legitimate Bitcoin endpoint. A direct version observation is stronger and can supersede gossip for the endpoint; it still does not establish Gateway compatibility. Store those evidence sources separately. Core itself overwrites gossip services on relevant outbound version receipt: [net_processing.cpp:3606–3611](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/src/net_processing.cpp#L3606-L3611).

## What BIP 434 proves

BIP 434 requires protocol version >=70017, forbids sending feature messages to peers below 70017, and places feature negotiation between version and verack. Feature identifiers are 4–80 bytes; feature data is at most 512 bytes; canonical CompactSize and complete payload parsing matter. Unknown valid features are ignored. Application messages introduced by a feature cannot be sent after verack to a peer that did not indicate support. [Pinned specification](https://github.com/bitcoin/bips/blob/b14d7c34e5ffa4dd910eeba3df4f92af6a9609d4/bip-0434.md#L75-L178).

Core v31.1 advertises **70016**, so Gateway must not send it BIP 434 feature messages. The BIP reference implementation [PR 35221](https://github.com/bitcoin/bitcoin/pull/35221) merged master on 2026-06-10; master support is distinct from the pinned release. [v31.1 protocol version](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/src/node/protocol_version.h#L9-L12).

Inference: an accepted Gateway feature declaration plus completed compatible Gateway hello establishes current endpoint protocol behavior. Neither authenticates a durable peer identity or proves capabilities, correct index answers, Bitcoin service availability, honesty, or independence from other peers. Anyone can copy the identifier and a valid hello. Reserve stronger evidence labels for service-specific checks. Even if transport authentication is added later, identity authenticity and answer correctness remain separate properties.

## Heat-seeking: replace a topology claim with a measurable yield hypothesis

The useful observation is `source S supplied candidate E at time T; a subsequent direct probe had result R`. Do not reinterpret it as `S is connected to E`, or as a shortest-path edge toward a Gateway cluster. Addrman sampling, long caches, address aging, broad gossip and unioned flags can erase a geographic or graph-local gradient. There may still be an empirical correlation between introducer and useful candidate yield, but it must outperform a diversity-preserving baseline under controlled trials.

Proposed minimal scheduler, before any Gateway is found:

1. Keep separate bounded queues for previously compatible endpoints, precise bit hints, suspicious masks, and unbiased Bitcoin exploration. Within each, deduplicate by normalized endpoint and apply cooldowns, failure backoff and finite retention.
2. Give precise hints a bounded preferential budget, not exclusive control. A configurable exploration floor and per-introducer/per-network-group caps prevent a rumor stream from monopolizing probes.
3. Score an introducer using **new directly compatible endpoints per unit probe cost**, with decay and a minimum sample requirement. Deduplicate repeated returns before crediting it. A low score is local scheduling evidence, not a public dishonesty accusation.
4. Persist locally useful observations without publicly exporting the encounter graph. Treat cached repeated samples as low novelty, not new confirmations. Do not evade Core's caching through address churn.
5. Stop treating the first successful hello as completion: retain a stable duplex session and collect a small diverse reserve. Otherwise reconnect churn wastes the successful entrance.

After first contact, bounded Gateway peer exchange can return expiring endpoint hints for directly supported protocol families, with explicit publication consent. Verify every new endpoint directly. Prefer repairing that compatible set before falling back to Bitcoin exploration; retain a small fallback/exploration path to avoid self-sealing eclipse. Introducer identity, endpoint network diversity and provider identity must remain distinct. Peer exchange improves connected-component discovery, but cannot summon an isolated Gateway component whose endpoints nobody knows.

No algorithm can guarantee discovery if there are zero reachable Gateway endpoints in the observable address population. Density, censorship, churn and correlated samples matter. A simplistic independent-sampling success formula would conceal these conditions and is not an operational latency prediction.

## Narrow decentralized entrance options

1. **Bitcoin-capable Gateway participants:** multiple independent operators run a shared Bitcoin-P2P-compatible endpoint that actually delivers advertised Bitcoin services and negotiates Gateway. This could be an adapter backed by Core, but a separate unmodified Core listener does not automatically advertise another port, set bit 25 or negotiate Gateway. Serving advertised Bitcoin requests is a substantive implementation obligation. Prove it rather than renaming a sidecar a full node.
2. **User-supplied/imported compatible endpoints:** transparent optional bootstrap hints from independent people, installations or signed configurations. This retains choice and direct verification, but it is not the brief's zero-known-Gateway Bitcoin-only entrance. Label the distinction in the product and tests.
3. **Future explicit address-propagation support:** a policy change or separate peer exchange among willing participants. This can be permissionless to implement, but must not be described as an ability of present stock Core.

A single hard-coded operator endpoint would make the trial easy while failing to prove the proposed decentralized entrance. Conversely, prohibiting every optional manual recovery mechanism does not make an unavailable bootstrap decentralized; it only makes recovery impossible.

## Proposed controlled experiments — not run

Use pinned stock binaries and source hashes, fresh independent datadirs, fixed initial populations, captured handshake/addr/getaddr traces, recorded configuration and repeatable random seeds. Adapt Core's [existing address-relay tests](https://github.com/bitcoin/bitcoin/blob/9be056a8a72b624dae9623b2f7bded92c2a21c91/test/functional/p2p_addr_relay.py), but do not confuse reading them with executing them. Keep the stock nodes unmodified. Use isolated routing with routable-form test addresses and no route to public peers: loopback/private-only gossip fixtures can fail IsRoutable before reaching the service-bit rule. Separate deliberately injected P2P evidence from real serving endpoints.

| Genuine Bitcoin entrance | Fresh Gateway knows Bitcoin peers only; a truthful Bitcoin-serving Gateway participant enters through ordinary gossip, with no direct fixture/seed leaked to the seeker | Discovery, allowed BIP 434 negotiation, completed hello, retained duplex session, elapsed time and all probe costs. |

Repeat across realistic Gateway densities and churn. Publish unsuccessful trials and censoring at the time limit. Compare metrics with uncertainty across independent seeds; do not report a single favorable run as convergence. A source review supports the filtering conclusion now; only these experiments can establish whether any surviving first-contact mechanism and source-yield heuristic are operationally useful.

## Gateway scheduler and ledger: independent code follow-up

Reviewed local files from Gateway commit `7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2` (the audit-brief-only commit following the intended code baseline). These are source-trace findings; this follow-up did not execute tests or change production code.

### 1. History exhaustion also disables recovery of known Gateway peers — high priority

`intakeBlockedLocked` becomes true at the record cap or byte limit. `maintainDiscovery` uses it to set `seek=false`; the scheduler then suppresses both candidate and search roles. Previously negotiated Gateway endpoints are in the specific/retry bucket, so ordinary transport scheduling does not reconnect them. Consequently, a full history ledger can strand already known Gateway membership after disconnect or restart, even though reconnecting requires no new endpoint record. New manual endpoints also use the blocked admission path. The API permits only raising the budget, up to 500,000 records/1 GiB; it refuses shrinking away history. This is a liveness consequence of the exact-history policy, not just an observability warning. [intake gate](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_ledger_053.go#L126-L128), [seek gate](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/network_052.go#L200-L225), [role suppression](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_scheduler_053.go#L96-L121), [budget API](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_api_053.go#L110-L131).

Small repair: separate `canAdmitNewEndpoint`, `canExplore`, `canReconnectKnownMember` and persistence health. Continue bounded, durably recorded reconnects of known endpoints when admission is full. Reserve a small explicit/manual recovery capacity. A subsequent migration can archive or expire old unverified records while preserving honest aggregate loss/coverage counters; never silently relabel bounded retention as complete lifetime history. Regression condition: fill history exactly to MaxRecords, disconnect the only known compatible peer, advance its cooldown, and assert its reconnect is planned while new gossip admission remains blocked.

### 2. Previously negotiated membership is not a dedicated recovery priority

`workBucket053` puts previously negotiated endpoints and unverified precise hints into the same evidence class. An attempted known Gateway competes with all attempted precise hints in bucket 3; fresh bucket 2 generally leads, with retry preference only on one in four opportunities in that class. Fair rotation is valuable but does not implement preferential mesh restoration. Faster failure backoff also requires prior BOD success, rather than generic Gateway compatibility. [bucket assignment and scheduling](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_scheduler_053.go#L8-L31), [candidate turn policy](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_scheduler_053.go#L111-L129), [backoff](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_ledger_053.go#L226-L252).

Small repair: a small due-known-compatible queue before unverified candidate work while the membership target is unmet. Retain bounded weak-hint and unbiased exploration opportunities; do not erase the existing all-bits classification or cooldown history. Test known-member recovery against a continuous stream of new precise false hints and a large attempted-hint backlog.

### 3. Role accounting and the target still couple generic membership to BOD

The scheduler counts each role separately, but candidate capacity checks only `gateway_candidate`; retained `gateway_member` and `gateway_service` sockets do not consume that per-role limit. The global socket cap still bounds total use. With defaults, three Bitcoin transports, two retained Gateways and two extra candidates can occupy all seven sockets, leaving no search socket at that instant. Meanwhile `seek` compares the target to successful BOD providers, not compatible Gateway members, so a healthy generic Gateway mesh keeps searching for BOD. `retainGatewaySessionsLocked` is already a useful bounded membership mechanism, but its role promotion exposes this accounting mismatch. [capacity](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_scheduler_053.go#L75-L108), [BOD usefulness](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/network_052.go#L155-L162), [membership promotion](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_quality_054.go#L91-L124).

Small repair: explicitly budget retained compatible membership, temporary probes and app-requested provider discovery. State whether borrowing idle capacity is intended; restore reserved exploration capacity when demand appears. BOD success should improve BOD provider preference, not define whether the root Gateway control plane is healthy.

### 4. The bounded working set does not bound resident ledger cost or lock duration

All ledger rows stay in `n.ledger` and `ledgerOrder`; only the approximately 4,096-entry frontier is disposable. Refill rebuilds all six classes and can scan the entire history for each class, including empty or ineligible classes. Maintenance runs every second under `n.mu`. Persistence also holds that mutex through row sorting, JSON generation, checkpoint rewriting, file sync and rename. `touchLocked` marshals each updated record while locked. The default 250,000-record/512-MiB *serialized* budget is neither an actual heap bound nor a latency bound. Existing 50k/250k resource tests are useful, but their presence does not establish acceptable p95/p99 lock stalls. [refill](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_scheduler_053.go#L33-L64), [tick](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/network_051.go#L216-L239), [persistence lock and checkpoint](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_persistence_053.go#L88-L212), [record sizing](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_ledger_053.go#L114-L125).

Small repair: bound records scanned per maintenance slice, retain per-class cursors, and maintain cached summary counters. Move immutable persistence snapshots and fsync outside the session mutex using generation-aware dirty tracking and a single writer. Preserve the existing commit-before-dial invariant: taking disk I/O outside the mutex must not accidentally make uncommitted dials possible. Measure lock hold/wait time, heap/RSS, disk bytes and recovery latency at full configured capacity before choosing a new database or replacing the WAL.

### 5. Introducer provenance exists; introducer yield learning and admission protection do not

The ledger retains the first `Source` plus at most four `Suppliers`; exact service-mask observations are correctly separated from aggregate OR-ed services. Refill caps a source to 512 entries **per bucket**, and limits a network group, but these are frontier constraints. There is no equivalent history-admission quota per introducer/network group or successful-Gateway-yield scheduler. Excluded private/unsupported endpoints and inbound ephemeral source identities still occupy exact ledger space. The 5,000-address budget per managed connection is a real defense, but multiple connections can cumulatively exhaust the lifetime ledger. Scoring only `Source` would also misattribute later helpful suppliers. [provenance and admission](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_ledger_053.go#L144-L222), [inbound source accounting](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_ledger_053.go#L395-L415), [managed connection budget](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/network_052.go#L116-L152), [mask classification](https://github.com/Blockamoto/gateway/blob/7f2ce1b9d39f2105c7ba0f116d5cd9925f0d2ff2/discovery_quality_054.go#L10-L51).

Low-cost next heat-seeker: retain the existing evidence classes and fairness; add the separate known-member recovery queue, bounded admission by source/group, and a small decaying per-introducer table of unique accepted candidates, completed probes, compatible outcomes and probe cost. Grant credit once per newly confirmed endpoint under an explicit attribution rule; cap credit shared among suppliers and never treat copied claims as independent evidence. Prefer measured novel yield within a fixed candidate/exploration budget. Track a source's cached-response novelty before increasing how often it is revisited: the current 30-minute revisit interval is much shorter than the stock-Core response cache lifetime. This requires no speculative graph crawler or DHT and must compete against the present scheduler at equal resource budgets.

The essential distinction is **bounded useful operational state plus honest bounded history**, rather than an ever-growing exact encounter archive whose admission limit becomes a network shutdown condition.

### Second-eye review of the app/index note

Reviewed `index-apps.md` independently after the scheduler follow-up. Its key boundaries are sound: passive manifests cannot establish an active provider; deterministic semantic roots must exclude local provenance while committing rules, dependencies, chain context and starting state; roots do not validate execution or completeness; and Bitmap's required upstream state depends on explicitly pinned query/eligibility semantics rather than requiring an entire Ord product or full sat inventory by assumption. Keep one implementation clarification visible: preserving wire-v1 framing still requires real registry-to-handler dispatch/session binding before arbitrary app payloads work. A registry manifest alone cannot supply that runtime path. The discovered root BOD-target coupling reinforces the need to separate membership health from app-specific provider demand.
