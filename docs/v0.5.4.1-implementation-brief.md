# Gateway Client v0.5.4.1
## Connection Stability, Symmetric Gateway Sessions, and a Deliberate BOD Request

**Date:** 24 September 2026  
**Baseline:** Gateway Client v0.5.4 test candidate  
**Release type:** narrow repair candidate  
**Rollback point:** v0.5.4 remains the known baseline if this patch destabilizes networking.

## 1. Purpose

v0.5.4.1 is not a new feature release. It is a deliberately small repair build based on live v0.5.4 QA across two Windows machines on the same LAN, one Core-backed and one standalone.

The release has three priorities, in this order:

1. **Keep ordinary Bitcoin transport usable and automatically replenished.**
2. **Make a negotiated Gateway connection symmetric, retained, and usable from either side of the same connection.**
3. **Prove a user-triggered BOD request over a negotiated Gateway path, without allowing ordinary Bitcoin retrieval to hide whether Gateway worked.**

Everything else is secondary. If these changes create regressions that cannot be isolated quickly, stop and revert to v0.5.4 with the brief, source diff, diagnostics, and test evidence preserved for Codex review.

## 2. QA observations that define this patch

These are user-observed facts from the v0.5.4 test session. They are evidence to reproduce, not automatic diagnoses.

### 2.1 Ordinary Bitcoin transport flaps

On the standalone machine, the displayed Bitcoin connection count repeatedly moved between connected peers and zero. When an ordinary Bitcoin peer was present, a block lookup could fetch from Bitcoin P2P. The user should not need to press Retry to keep a normal small transport pool alive.

Required interpretation: individual Bitcoin peers may disconnect normally, but the client should maintain and replenish a bounded pool. A request timeout must not casually destroy an otherwise healthy transport connection.

### 2.2 Gateway state is asymmetric

The Core-backed node showed a negotiated Gateway and a working/useful peer while the standalone node commonly showed one live Gateway connection but no demonstrated useful request. The connection then disappeared and later returned.

The test is on the same LAN, so it does not establish public Bitcoin-only discovery. It does establish a useful interoperability question: after the two clients have a negotiated socket, both sides should agree that Gateway was negotiated and each side should be able to use the connection according to the negotiated capabilities.

### 2.3 A real lookup reaches BOD fallback but cannot use a stable peer

The standalone machine attempted a 64-character transaction lookup while the relevant local headers were present. The failure reported, in substance:

> The value did not resolve as a transaction or block. Bitcoin peers did not serve the required block; an archival-peer attempt timed out; BOD fallback also failed because no connected BOD peer supplied the block.

This is useful evidence. The request path reached the BOD fallback, but the client did not have a usable retained BOD connection at the moment it needed one.

### 2.4 Clean uninstall appears improved

The user tested the v0.5.4 destructive uninstall path. Reinstallation began at setup step 1 with apparently new data, rather than jumping back to the previous ready state. Treat that as encouraging live QA, not a complete Windows deletion audit. Preserve and regression-test the v0.5.4 cleanup engine; do not redesign it in this patch.

## 3. Source-audit hypotheses to test before changing behavior

The implementation must audit these mechanisms rather than assuming the UI alone explains the fault.

### 3.1 Request timeout currently closes the whole managed session

In the v0.5.4 baseline, the shared managed-session request helper closes the peer when its request context expires. That means a slow `getheaders`, `getdata`, status, or BOD request can convert a request-level timeout into a transport-level disconnect.

Test this directly. If reproduced, change request timeout handling so a request can fail without automatically tearing down a socket that remains otherwise alive. Actual read/write failure, malformed protocol data, integrity failure, explicit disconnect, or liveness failure may still close the connection.

A late reply after a timed-out serialized request must be safely discarded before the next request rather than being mistaken for the next response.

### 3.2 Inbound Gateway sockets are tracked outside the outbound managed-session pool

The v0.5.4 listener tracks inbound sockets in the serving-side live inventory, while outbound Gateway/BOD requests use the managed Bitcoin session pool. This may create a state where one side sees a live negotiated inbound connection but cannot use that same socket for an outbound BOD request.

Audit and, if confirmed, make successfully negotiated inbound Gateway sockets first-class managed sessions after the Gateway hello exchange. One physical socket should not appear twice in Peers.

The connection is full duplex. A peer that dialed us must not become “receive-only” merely because of who opened TCP.

### 3.3 Negotiation and useful-service counters may describe different connection inventories

Audit every counter shown as `live`, `negotiated`, `BOD available`, `working`, and `useful`. A negotiated inbound socket and the same negotiated outbound socket must use the same definitions. Historical negotiation remains separate from current live state.

## 4. Required implementation behavior

### 4.1 Persistent Bitcoin transport

Maintain the existing bounded ordinary Bitcoin transport target. Losing one peer should start replacement automatically. Losing several peers must not make discovery stop permanently or require a manual Retry.

A request-level timeout is not automatically a peer disconnect. Keep the socket unless there is independent evidence that transport is dead or unsafe. Record request failure separately from transport failure.

Retain existing concurrency, address diversity, backoff, and global dial-rate controls. Do not solve flapping by opening an unbounded number of peers.

The header synchronizer, ordinary block fetcher, Gateway crawler, and module requests must share the connection manager without one job repeatedly destroying transport needed by the others.

### 4.2 Symmetric Gateway connection adoption

After a valid inbound Bitcoin + BIP 434 + Gateway hello negotiation, transfer that socket into the same managed-session abstraction used for outbound connections, or implement an equivalently safe full-duplex request multiplexer.

The resulting session must:

- remain one physical connection in Peers;
- record direction as inbound or outbound;
- expose Bitcoin, Gateway, and BOD capabilities from actual negotiation;
- accept bounded inbound requests according to serving/privacy settings;
- permit bounded outbound BOD requests over the same socket;
- answer ping/pong and retain ordinary address exchange where supported;
- survive past the short discovery probe lifetime simply because it is a negotiated Gateway member;
- be eligible for normal health checks without equating one failed BOD request with a dead TCP connection.

Do not weaken BIP 434 ordering or accept Gateway messages without negotiated support.

### 4.3 Reconnection knowledge

If a negotiated Gateway socket closes, retain evidence that the peer was compatible and try to reconnect according to normal policy when a dialable listener endpoint is known.

Do not treat the remote TCP source port of an inbound connection as its permanent Gateway listener. If this patch learns or infers a reciprocal listener endpoint, constrain it to the already-connected remote host and a legitimate advertised/configured Gateway port. Never turn it into an arbitrary third-party dial instruction.

For the v0.5.4.1 acceptance path, keeping the existing full-duplex socket stable is more important than inventing a new endpoint-advertisement protocol.

### 4.4 Deliberate BOD-only diagnostic request

Add a narrow QA control that proves the Gateway/BOD path directly. It must not silently fall back to ordinary Bitcoin P2P, Core RPC, mounted files, or a public HTTP service.

A suitable first test is a **BOD-only block-location request**, optionally followed by a block transfer when the peer advertises it. Use a non-genesis height such as block 1 by default, while allowing an explicit height for diagnostics.

The result must state:

- which live Gateway session was used;
- connection direction;
- Gateway/BOD negotiated versions;
- request type and target;
- whether a locator was returned;
- whether bytes were retrieved, and through which negotiated path;
- integrity/anchoring checks actually completed;
- elapsed time;
- exact failure if no current peer can answer.

A successful ordinary Bitcoin fetch must not cause this diagnostic to pass.

### 4.5 Truthful UI state

For the focused patch, prefer clearer state over visual redesign.

Show current live counts separately:

- Bitcoin transport connected;
- Gateway negotiated live;
- BOD capability live;
- useful BOD provider demonstrated.

Historical negotiation may still be shown, but label it historical. Avoid a generic `live` label when the user is specifically trying to learn whether Gateway negotiation completed.

Connection events should identify why a session closed: remote EOF, write failure, protocol violation, explicit user action, network disabled, transport liveness failure, or request timeout. A request timeout that leaves the socket open should be recorded as such.

## 5. Clean uninstall regression requirement

Do not expand cleanup scope in this patch unless a defect is reproduced. Preserve the v0.5.4 choices:

- **Remove application, keep Gateway data** remains the default.
- **Remove application and Gateway-owned data/settings** is explicit and destructive.

The destructive path includes Gateway-owned peer/discovery state, Bitcoin headers/cache/indexes, mounted-file locator sidecars, Satline/Ord local work, setup state, and configuration selected for deletion.

It must not delete mounted or external Bitcoin Core/Ord data, wallets, unrelated files, or user exports. A destructive uninstall followed by reinstall should start setup from the beginning with no imported Gateway peer ledger unless the user deliberately retained a separate profile.

This is a regression gate, not the main engineering focus of v0.5.4.1.

## 6. Explicit non-goals

Do **not** add these to v0.5.4.1:

- Gateway Chat;
- libp2p or another discovery overlay;
- a hard-coded Gateway bootstrap list;
- new Ord/sat/address indexing work;
- public-discovery speed tuning beyond what is necessary for connection replacement;
- a browser fork or companion redesign;
- a storage-format rewrite;
- new service-bit semantics;
- a broad UI redesign.

Gateway Chat remains a useful next capability once the transport can hold a connection. It should not become a diagnostic bandage over unstable networking.

## 7. Required tests

### A. Request timeout does not kill healthy transport

Create a managed Bitcoin session that completes the handshake and continues answering ping/pong but deliberately withholds one requested response. Let that request time out.

Pass conditions:

- the request returns a timeout;
- the session remains connected;
- a subsequent ping/pong or supported request succeeds;
- the UI/event log records request timeout separately from disconnection.

A real socket close or write failure must still remove the session.

### B. Bitcoin pool replenishment

Start three controlled ordinary peers. Disconnect one, then two, while eligible replacements are available.

Pass conditions:

- replacement begins automatically;
- the pool returns toward its target without a user Retry;
- headers/data remain able to select healthy peers;
- repeated request timeouts do not collapse all transport slots.

### C. Inbound Gateway becomes a bidirectional managed session

Client A dials client B and completes Bitcoin, BIP 434, Gateway, and BOD negotiation.

Pass conditions on both clients:

- exactly one physical socket is represented per side;
- both call it Gateway negotiated;
- both expose the same compatible BOD version;
- A can request a BOD status/location from B;
- B can request a BOD status/location from A over the already-established connection, without first opening a second TCP connection;
- privacy/serving settings are still enforced.

### D. Connection survives useful and non-useful service outcomes

Use one Gateway with no useful non-genesis sample and one with useful BOD coverage.

A negotiated membership connection must not be retired merely because a useful sample is unavailable. A request timeout or unsupported resource should not automatically destroy the member connection. Protocol incompatibility or integrity failure may do so where justified.

### E. Deliberate BOD-only request

From the standalone client, invoke the BOD-only diagnostic against a Core-backed Gateway server.

Pass conditions:

- no ordinary Bitcoin, Core, mounted-file, or HTTP fallback satisfies the diagnostic;
- block 1 location is returned by a currently negotiated BOD peer;
- if raw bytes are requested and supported, they pass the existing identity/Merkle/witness checks;
- provenance names the actual Gateway connection;
- a disconnected server gives an honest no-live-BOD-peer result.

### F. State symmetry and flapping trace

Capture both clients simultaneously for at least several maintenance and ping cycles. Compare live connection IDs, direction, negotiated protocols, request counts, disconnect reasons, and reconnect events.

The two sides need not display the same direction, but they must agree that the connection is Gateway-negotiated while it exists.

### G. v0.5.4 regressions

Re-run the existing discovery-ledger, noisy graph, weak-hint, stable advertisement, integrity, privacy, setup, and cleanup tests. The patch must not erase v0.5.4’s fixes merely to keep one LAN socket alive.

### H. Windows evidence remains separate

Cross-compilation is not native Windows acceptance. Record which checks ran in Linux fixtures, which ran on actual Windows machines, and which remain user QA. Do not declare the flapping fixed from a unit test alone.

## 8. Suggested implementation order

1. Preserve the exact v0.5.4 source and artifact hashes.
2. Add baseline reproductions for request-timeout teardown and inbound request asymmetry.
3. Change request timeout handling without weakening true connection-failure handling.
4. Make inbound negotiated Gateway sessions full-duplex and part of the common session inventory.
5. Make live/negotiated/BOD/useful counters derive from that common inventory.
6. Add the BOD-only diagnostic action and minimal UI surface.
7. Run focused tests, then the full race-enabled regression suite.
8. Cross-build Windows artifacts and audit installer/portable payload equality.
9. Package the brief, source diff, test evidence, checksums, and rollback note with the candidate.
10. Perform live Windows QA. If the patch destabilizes v0.5.4 behavior, stop and revert rather than layering compensating hacks.

## 9. Live QA recipe for v0.5.4.1

Use fresh or explicitly known profiles on both machines.

1. Start the Core-backed Gateway node with serving enabled.
2. Start the standalone Gateway client. Do not press Retry unless the automatic recovery itself is under test.
3. Confirm ordinary Bitcoin transport reaches and maintains its configured bounded pool.
4. Wait for the two Gateway clients to connect by the currently enabled discovery path. For the same-LAN test, LAN discovery is acceptable but must be labelled as such.
5. Confirm both sides show **Gateway negotiated live**, not just one side.
6. Leave the session running across multiple ping/maintenance cycles and observe whether it stays connected.
7. Run the new **Test BOD path** action for block 1 from the standalone client.
8. Confirm the Core-backed node records the matching request and the standalone client records the matching response/provenance.
9. Stop the Core-backed Gateway process. Confirm the standalone client reports the lost connection and automatically keeps/replenishes ordinary Bitcoin transport.
10. Restart the Gateway server. Confirm bounded recovery without manual Retry when a reconnect route is available.

Public discovery from the brother’s separate network is a distinct subsequent test. It should not be conflated with this LAN transport/negotiation repair.

## 10. Release gate

v0.5.4.1 is worth handing forward only if it demonstrates all of the following in controlled tests:

- request-level timeout no longer causes unjustified transport teardown;
- ordinary Bitcoin peers are automatically replenished;
- an inbound negotiated Gateway socket becomes a full-duplex managed session;
- both ends report current Gateway negotiation consistently;
- a BOD-only request can be initiated from either side of that connection;
- existing v0.5.4 discovery, integrity, privacy, and cleanup tests remain green.

The real-machine gate is stricter: the user’s standalone Windows machine must hold the connection long enough to complete the deliberate BOD request. Until that happens, the patch is a test candidate, not a resolved networking milestone.

## Final acceptance statement

> v0.5.4.1 keeps the floorboards still. Bitcoin transport recovers without babysitting, Gateway negotiation means the same thing on both ends of a live socket, and a standalone client can deliberately ask its connected Gateway peer for BOD data and receive an answer without another transport quietly taking credit.
